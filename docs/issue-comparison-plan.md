# 同選區候選人議題與政見比較：實作與呈現提案

日期：2026-11-16。本文是開發提案，尚未執行政見分析或改動正式網站。
需求中的「證件」暫按「政見」理解。範圍是同一屆、同一縣市、同一職位的直轄市長／縣（市）長候選人；鄉鎮市長若後續擴充，另用相應選區分組。

## 1. 建議做成什麼

新增「同選區政見比較」：選縣市、選議題，先讀到各候選人共同主張、具體差異與目前無法判斷的部分，再展開每項結論的原文證據。

主要回答：

1. 候選人對同一個具體問題提出什麼做法？
2. 差異在目標、政策工具、對象、規模、財源、時程，還是附帶條件？
3. 哪些是明確相反的立場，哪些只是不同側重、可以並行的措施？
4. 哪些候選人目前只有概括表態、說法不一致，或收錄資料不足？

貼文數與議題比例仍可當背景資訊，但不能直接代表支持、反對、政見完整度或施政優劣。候選人自述的施政成果、數字和指控，一律以「候選人表示」歸屬；本功能整理主張，不替其內容完成事實查核。

## 3. 先把所有候選人與來源對齊

### 候選人與選區

- 比較群組使用 `electionYear + county + category + districtKey`，避免混入不同職位或不同屆的說法。
- 官方名單決定參選人集合，社群監看名單只負責補內容，不能拿來決定誰有資格被列出。
- 建立 `candidate_identity_map.csv`，明確連結官方名冊列與既有穩定 `candidate_id`，附查證來源。官方號次 ID 可能受補公告影響，不拿來當跨版本的人物 ID。
- 不能只用姓名自動合併；同名者至少核對縣市、參選職位與官方身分。未確定者保留未連結狀態。
- 未有號次時以登記名冊與審定來源補列，標示「號次待公告／資格待確認」；官方確認撤回或不合格者移到歷史區，保留版本。

### 資料來源

優先取得選舉公報候選人政見欄、競選官網政策頁與白皮書，再納入本人／競選團隊已驗證的貼文與直接發言。公報由選委會發布，但政見內容仍是候選人提出，不能標成選委會背書。

- 每份資料存來源 URL、來源類型、候選人、發布時間、抓取時間、原始內容雜湊與版本。
- PDF 保留頁碼及版面位置；掃描 PDF／圖片使用 OCR，影片使用可靠逐字稿及時間碼。缺文字、辨識有疑義時，不以標題或圖片檔名猜主張。
- 政府公務帳號的行政公告另標為行政資訊，除非本人明確承諾延續或提出政策，不轉成競選政見。
- 轉貼、引用對手、支持者發文與政黨通稿，先辨認說話者。只保存有明確本人認同證據的主張；不能把對手的話歸給候選人。
- 新聞可協助找到原始來源，不單憑記者歸納建立本人政見。
- 保留來源快照與歷史版本；刪文或改文標示狀態，不能抹除先前證據。

預設分析本屆選舉年 1/1 起至資料截止日的內容，頁面明示範圍；同屆仍有效的較早正式政見另列「較早發布」，不偷偷混入近期時間窗。沒有發布日期的文件標為日期不詳，抓取日不能冒充發表日。

## 4. AI 分四個階段執行，全部使用 Sky-Quality

這四個階段是批次資料工作，不需要四個代理或互動聊天。閱讀者只讀預先產出的靜態結果。

### A. 抽取逐條主張

每篇來源分段，保留鄰近上下文；交給 `sky-quality` 回傳嚴格 JSON。每一條只表達一個可核對的主張，內容包括：

| 欄位 | 用途 |
|---|---|
| `claimId / candidateId / raceKey` | 穩定追溯到候選人與選區 |
| `topicId / questionId / policyObject` | 大議題、具體問題、針對的政策或建設 |
| `assertionType` | 政策承諾、明確立場、批評、成果陳述、一般願景 |
| `speaker / attribution` | 誰說的，是否為候選人本人明確認同 |
| `stance` | 支持、反對、附條件支持、提出方案、未明確表態；必須相對於具體政策問題 |
| `action / targetGroup / geography` | 做法、受益對象、適用地域 |
| `quantity / unit / baseline / metricScope` | 數量、單位、基準、是新增量還是累計量 |
| `funding / timeline / conditions` | 財源、時程、前提；沒寫的一律留空 |
| `evidence[]` | 來源版本 ID、原文引句、段落／頁碼／時間碼、發布日 |
| `extractionStatus / uncertaintyReason` | 有效、待辨識、歸屬不明等原因 |

不可從黨籍補立場、從口號補政策工具、從批評補替代方案。提示詞將原始文件明確當成待分析資料，不採納其中任何對模型的指令。

### B. 對齊同一個政策問題

先使用既有「住宅、交通、社福」等大分類，再建立地方化子題，例如「社宅新增供給」「租屋補助資格」「某條捷運是否續建」「公車班距」。縣市議題還要容納農漁業、離島交通、供水等，不能硬套都市題目。

由同選區所有人的主張共同產生問題集合，再用穩定 `questionId` 對齊；低發文量候選人的獨特主張也要保留。關鍵字和向量搜尋只能協助召回，最後是否同題由模型依政策對象、地域、時間及條件確認。

例如「新增社宅」與「增加租屋補助」都屬住宅，但不代表彼此反對；「反對某路線目前的規劃」也不能改寫成「反對捷運」。

同文跨平台建立 `contentClusterId`，同一主張重複發表保留所有來源，只算一個主張；同一候選人新增加條件的版本仍須另外抽取。不能把跨平台轉貼當成獨立佐證。

### C. 先彙整每位候選人，再做同選區比較

每個「候選人 × 政策問題」建立主張摘要及證據，之後才比較多人。不要把所有原始貼文塞進單次請求；分段抽取與完整主張清單可避免發文多的人佔滿上下文。

比較結果使用以下關係：

- **方向相近**：針對同一問題提出相近方向，仍說明條件或工具差別。
- **做法／側重不同**：政策工具或優先順序不同，未必互斥。
- **明確分歧**：對同一政策對象、範圍與條件，一方明確支持、另一方明確反對。
- **尚無法比較**：缺其中一方明確說法、數量口徑不同、日期不詳或資料取得不全。

數字比較須先確認新增／累計、戶／床／人、任期／年度、適用地域等口徑。不能直接說「2 萬比 1 萬更多」，除非口徑可比。

同一人前後說法不同，保留日期與兩方原文；明確宣告修正時標示「已更新主張」，沒有明確修正時標示「收錄資料中存在不同說法」。不能用最新一篇默默覆蓋，也不能自動定性為「跳票」。

每段比較摘要附 `claimIds`；「A 與 B 的差異」必須同時有 A、B 的證據。摘要長度相當，避免一人完整說明、另一人只剩負面標籤。

### D. 獨立檢核

再以一次 `sky-quality` 請求，直接看結論、引用片段與足夠原始上下文，逐句檢查是否有支持、數字是否一致、說話者是否正確，以及是否把缺資料寫成反對。不是只檢查上一輪摘要。

同模型第二次檢查可降低錯誤，但不是獨立事實查核或正確性保證。程式另做硬性驗證：

- 引句必須在指定來源版本存在；必要的空白／換行正規化須有固定規則。
- 所有引用 ID、候選人及選區正確且可解析。
- 數字、單位、日期與原文一致，未公開欄位不被補值。
- 無資料者不能出現支持／反對判定。
- 明確分歧兩邊都有直接主張，反例與附帶條件不能被省略。

檢查失敗時自動重試並限制次數；仍不通過就只呈現已驗證原文及「目前無法形成可靠比較」。不需要新增人工核准流程。AI 自報信心只當診斷資料，不能顯示為「正確率 95%」。

## 5. Sky-Quality 接法、快取與更新

沿用現有 gateway、`MAYOR_AI_API_KEY` 與 Responses API 的結構化輸出方式。新增分析專用設定，避免改動既有分類器的預設：

```dotenv
# 提議新增，現在程式尚未讀取這些設定
MAYOR_COMPARISON_MODEL=sky-quality
MAYOR_COMPARISON_REASONING_EFFORT=medium
```

`sky-quality` 是請求別名，不預設等同某一家固定模型。正式開發先做小型相容性測試，確認 gateway 支援此別名、JSON Schema 與允許的推理設定；不支援就回報錯誤，不自動換成其他模型。上面的 `medium` 是建議值，需以 gateway 實際能力確認，不能直接沿用既有全域 `none`。

建議將 `classify_context.py` 的 HTTP、schema 與用量紀錄抽成共用 client，讓各階段各自傳入模型與推理設定，避免依賴分類器全域設定。新功能的 OCR／逐字稿語意整理、抽取、對齊、摘要與語意檢核都指定 `sky-quality`；既有日常貼文分類可維持原設定。

- 每次記錄 `requestedModel`、實際 `model`、模型是否由 gateway 明確回傳、prompt/schema/taxonomy 版本、輸入雜湊、時間、token 與失敗原因。
- 若 gateway 沒回實際模型，標示「實際模型未回報」，不能把別名宣稱成已確認的底層模型。
- 抽取快取依來源內容版本與分析版本；比較快取依該選區該問題全部主張及覆蓋狀態。新資料只重算受影響區塊。
- 快取清單保存實際模型。需要比較不同模型版本時明確強制重算；別名更換對應不默默造成所有歷史資料反覆付費。
- 對單次請求設輸入／輸出上限、有限重試與退避，並設單輪及每日 token 預算。實際費用依 gateway 費率與用量回報；沒有單價就報 token，不能編估美元數字。
- 達額度或暫時失敗時延後工作，保留上一份通過驗證的結果並顯示其資料截止日；新來源仍標示「待分析」。不得把舊結果標成已讀取最新資料。

## 6. 如何接入現有檔案與排程

以下均為建議新增檔案／步驟，尚未存在：

| 檔案／模組 | 責任 |
|---|---|
| `data/sources/candidate_identity_map.csv` | 人物穩定 ID 與官方名冊對照 |
| `data/sources/policy_documents.csv` | 公報、白皮書、政策頁來源與查證 |
| `data/sources/issue_questions.json` | 版本化子題、問題定義與可比較欄位 |
| `scripts/policy_document_fetcher.py` | 文件抓取、原始版本與文字／頁碼對照 |
| `scripts/extract_policy_claims.py` | 分段與逐條主張抽取 |
| `scripts/build_issue_comparisons.py` | 問題對齊、候選人摘要與同選區比較 |
| `scripts/verify_issue_comparisons.py` | 引用、數字、歸屬與語意檢核 |
| `scripts/schemas/policy-*.schema.json` | 各階段嚴格資料契約 |
| `scripts/render/comparison.py` | 靜態比較頁與原文證據 |
| `site/assets/pages/comparison.{css,js}` | 篩選、展開來源、手機版呈現 |

建議資料流：

```text
官方名冊與身分對照 ──────────────────────────┐
已驗證貼文 + 公報／白皮書／政策頁             │
    ↓ 來源快照、分段、跨平台同文去重           │
sky-quality：主張抽取 → 問題對齊              │
    ↓                                      │
候選人 × 具體問題的主張摘要 ←────────────────┘
    ↓ sky-quality：同選區比較
程式驗證 + sky-quality：逐句證據檢核
    ↓
版本化比較資料 → 公開 JSON → 靜態頁面
```

接入 `run_pipeline.py` 時在建站前完成上述步驟；比較的來源讀取不能只用 `read_classified_candidates()`，以免舊分類尚未完成的貼文或回應文被錯誤排除。獨立處理取得的可靠文本及待分析狀態。

來源快照、主張與比較版本使用獨立 append-only 歷史資料，不修改現有貼文歷史列。新增要保存到 `data` 分支的檔案時，必須同步擴充 `sync_pipeline_data.py` 的檔案清單及還原測試；大型 PDF／圖片以持久化物件儲存及內容雜湊索引保存，不能只放會清掉的 `state/`。

公開網站只讀完成檢核的產物；新流程失敗可保留前次結果，不能發佈未通過的比較。

建議路徑：

```text
/compare/                                      縣市選擇
/compare/2026/<county>/<category>/              同選區議題入口
/compare/2026/<county>/<category>/<topic>/      完整議題比較
/api/comparisons/2026/<county>/<category>/<topic>.json
```

JSON 至少包含 `raceKey / asOf / generatedAt / window / rosterVersion / coverage / questions / candidates / findings / evidence / analysis`。`findings` 存結論與 `claimIds`，`evidence` 存原文定位；頁面、API、分享結果使用同一版本。新路徑需要加入 sitemap、產物驗證、生成目錄忽略規則與站內入口。

## 7. 比較頁如何呈現

### 第一層：先說最有用的差異

頁首為縣市、職位、議題與資料截止日，接著用 2–4 句回答「共通方向」「主要做法差異」「哪些問題目前不能比較」。沒有可靠分歧就如實顯示，不為了精彩強行製造對立。

清楚顯示名單涵蓋狀態與資料取得狀態，例如「已列入所有已確認候選人；部分候選人的政策來源仍待取得」。只有名單對帳完成才顯示「所有」。不能把「已追蹤者」當成全體候選人。

### 第二層：具體問題對照表

每列為同一個具體問題，每欄為候選人；內容依序是短摘要、條件／未揭露事項，以及原文入口。候選人按已公告號次排列，未有號次者另依公開規則排序；不按貼文量或 AI 評分排高低。

候選人多時可固定問題欄並橫向捲動、提供兩人／多人篩選，但預設保留全體名單與覆蓋提示。手機改成「一個問題 → 所有候選人的直式卡片」，避免必須左右來回才能讀完一句話。

清楚區分以下情況：

- 「已找到明確主張」
- 「只有概括方向，未見具體措施」
- 「在已收錄資料中未找到明確說法」
- 「來源尚未取得／抓取失敗」
- 「來源已取得，待分析」
- 「收錄說法不同，請看日期與條件」

未知不能用反對符號或 0 分表示；資料不足也不能改寫成「沒有政見」。

### 第三層：可追溯原文

每個摘要都能展開原文引句、發布日、來源類型、完整上下文入口、PDF 頁碼／影片時間碼與歷史版本。原文已失效時清楚標「原始連結失效，以下為收錄時版本」。每個獨立主張至少有一項有效證據，不以固定三篇貼文數作為立場門檻。

### 第四層：變更與方法

顯示候選人政策的版本時間軸，以及「分析更新日」與「來源截止日」兩種時間。方法說明可展開，交代 AI 整理範圍、原文來源與錯誤回報；一般閱讀流程不需要先理解模型設定。

既有 `/spectrum/` 保留「談什麼」的議題比例，新增入口前往本功能的「具體怎麼主張」。候選人頁與官方候選人名單頁也加入同選區比較入口。

視覺沿用本站字體、深淺色及紫羅蘭 accent；支持／反對以文字描述，配色不帶政黨傾向。避免雷達圖、左右立場軸、總分或「誰最好」排名，這些無法忠實表達有條件的多維政策。

互動呈現示意見同目錄 `issue-comparison-mockup.html`。其縣市、人物、引句與主張全部為虛構，只用來檢視資訊層次，不能當成選舉分析結果。

## 8. 實作順序與驗收

1. **先做來源與名單對帳**：全 22 縣市都可進入；完整列出已確認及待公告參選人，呈現身分／來源狀態。選一個資料較齊全的選區，以住宅、交通、托育三題跑通流程。
2. **做可驗證的分析資料**：Sky-Quality 抽取、對齊、比較、檢核，先輸出可追溯 JSON。試點也必須列全該選區候選人。
3. **接上比較頁**：摘要、問題表、原文證據與手機卡片，再連接既有候選人頁及議題頁。
4. **擴展全國並增量更新**：按來源可用狀態補完公報與貼文，地方子題保留在各縣市；覆蓋不足照樣顯示狀態，不虛構內容。

需要有意義的驗證案例：

- 引用對手的反對說法，不會被歸成發文者反對。
- 回應文中明確承諾的政策可以被抽取。
- 「新增 1 萬戶」和「累計 2 萬戶」被標為口徑不同。
- 「支持附條件的路線方案」不會變成無條件支持整個建設。
- 同文跨平台不會灌大證據數；新增加條件的內容不被去重吃掉。
- 待公告號次、無已驗證帳號、抓取失敗的候選人仍在名單上。
- 修改／刪除來源、前後說法不同時保留時間與證據版本。
- 引用不存在、缺乏其中一方主張、AI 超額或 gateway 不支援別名時，不能發佈新結論。

用涵蓋上述風險的人工標註樣本校對抽取、歸屬與差異類型；這是開發驗證，不是每次發佈的人工簽核。程式檢查要求候選人集合對帳、引用可定位、跨選區混入及無證據結論等重大錯誤為零；語意品質另記錄樣本錯誤率及修訂，不宣稱零錯誤保證。

本提案與示意頁不呼叫付費 AI、不重跑抓取、不執行 pipeline、不發佈網站。下一階段可直接依以上資料契約與試點順序實作。
